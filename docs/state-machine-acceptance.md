# 狀態機與 Windows 真實操作驗收

## 可直接交給代理的指令

> 嚴格按照 docs/state-machine.md 與 docs/state-machine-acceptance.md 執行一輪完整驗收。先確認原始碼版本與打包產物一致，再跑自動測試，使用 computer-use 操作 Windows 實際封裝程式，逐項完成所有案例與子分支。每項記錄預期、實際結果及證據。不得用程式填值、合成事件或自動接受對話框代替真實輸入與原生對話框驗證。未執行、無法重現測試前提或只有間接證據的項目標記 BLOCKED；任何偏差標記 FAIL。修正後重跑失敗案例、相關狀態交互及完整自動測試，重建後重跑整輪封裝驗收。最後提供案例報告，只有全部必測項目 PASS 才能判定整輪通過。不要發布版本。

## 執行前提與證據

1. 記錄 Git SHA、dirty diff、Windows 版本、Electron 版本、輸入法名稱／模式、螢幕縮放、視窗尺寸及測試時間。
2. 使用 lockfile 安裝依賴，執行 `npm test`、`npm run build`；本機封裝使用可辨識測試版本與 `--publish never`。記錄 EXE SHA-256 與封裝版本。測試工具放在隔離目錄，避免安裝工具改變產品依賴。
3. 所有測試存檔、執行用 EXE 副本、profile、截圖、日誌和結果放在專案絕對路徑解析出的 `test-data/runtime/acceptance-<run-id>/`；固定素材放 `test-data/fixtures/`。只操作該次建立的假資料。
4. 使用 computer-use 技能所提供的 Windows 原生控制。先定位目標視窗；點擊、實際按鍵輸入、原生確認框與視窗切換均經由該工具執行。
5. 滑鼠點輸入框後用鍵盤打字；中文使用 Windows IME 的逐鍵組字／選字。貼上文字與直接填值不能充當 IME 驗收證據。無法操作真實 IME 時標記該分支 BLOCKED。
6. 可用檔案工具準備故障素材、讀取測試 JSON／備份／hash；可用單元測試與 smoke 檢查內部狀態。這些結果與原生互動證據分開記錄。
7. 每項記錄操作前後畫面及磁碟結果；焦點案例額外記錄插入游標、實際鍵入文字、選取卡片與文字落在哪一欄。不要用觀察到的卡片顏色推定內部 ID 已正確。
8. 自動測試、computer use 與故障注入三種證據共同構成一輪。每個分支獨立標記 PASS、FAIL 或 BLOCKED；只有條件確實不適用於此次平台時才可記 N/A，並說明理由。

## 標準測試資料

用 UI 建立存檔 A：產線 A、B、C；A 有機台 A1、A2，B 有 B1，C 無機台。A1 有耗材 X、Y。另建立空存檔 B。維護素材日期相對於本次本地日期產生：昨天、今天、+1、+7、+8 天，並保留同名不同父層的項目。每個破壞性案例從獨立測試副本開始。

## 故障判定與回歸要求

- A03、A07、A09、A14 的原生視窗／確認框／IME 流程不得由 jsdom 的 confirm stub、Playwright 自動接受對話框或合成 composition 事件取代。
- 若只能 Alt-Tab 後恢復，原案例判 FAIL；恢復操作只作診斷證據。不能把「切視窗後正常」算成通過，也不能用排序選取測試替代原生焦點復現。
- 等待以可觀察的狀態完成為準，記錄逾時；不得插入任意長等待使競態消失。確認刪除後第一下點擊及第一段輸入要單獨記錄。
- 刪除、首次貼上、排序、切父層及新增子項必須串接，核對子項真正存到哪個父層。單步成功不代替交互流程通過。
- 一項失敗後保留截圖、步驟和測試資料。修正產品程式後建立新的產物 hash，舊產物的驗收結果不得沿用到新產物。
- 第 14 節列出的自動化缺口可由本輪 computer use 提供人工式證據，但仍保留「自動測試未覆蓋」標記。工具或故障環境不足時記 BLOCKED，不能推定成功。

## 每輪報告

在本輪 runtime 目錄保存 `report.md`，至少包含：

```text
原始碼 SHA／dirty diff：
EXE 絕對路徑／版本／SHA-256：
Windows／Electron／輸入法／縮放／視窗尺寸：
自動測試命令、退出碼與結果：
案例 ID＋子分支 | 前置狀態 | 實際操作 | 預期 | 實際 | PASS/FAIL/BLOCKED/N/A | 截圖/JSON/日誌
偏差與復現步驟：
修正後重跑範圍及新產物 hash：
總計：PASS / FAIL / BLOCKED / N/A
結論：整輪通過／失敗／未完成
```

只有所有適用案例與子分支都有證據、FAIL=0、BLOCKED=0、自動檢查成功且產物一致，結論才可寫「本版本在所列環境與驗收範圍內全部符合預期」。未列入案例的操作組合不在此結論範圍內。新增使用者復現路徑時，先擴充此清單，再作為後续每輪的必測項。
